#  Симулятор Банкомата (Automated Teller Machine)

##  Опис функціоналу
Цей проєкт — десктопний додаток на базі Windows Forms (C#), що симулює роботу реального банкомата. Проєкт побудований з використанням принципів об'єктно-орієнтованого програмування (SOLID) та класичних патернів проєктування. 

**Основні функції:**
* **Автентифікація:** Вхід за номером картки та PIN-кодом. Блокування картки після 3 невдалих спроб.
* **Перевірка балансу:** Відображення актуального залишку на рахунку.
* **Зняття готівки:** Розумний алгоритм видачі грошей з урахуванням наявності фізичних купюр у касетах банкомата. Можливість вибору стратегії видачі (стандартними або дрібними купюрами).
* **Переказ коштів:** Транзакції між різними рахунками з автоматичним оновленням балансів.
* **Історія транзакцій:** Логування всіх операцій (зняття, перекази, поповнення) у вигляді детальної виписки.
* **Сервісний режим (Інкасація):** Вхід за логіном `ADMIN` та паролем `8888` для перевірки та поповнення фізичного залишку купюр у сейфі.

# Programming Principles
Під час розробки було дотримано наступних принципів програмування:

* **Single Responsibility Principle (SRP):** Кожен клас має лише одну зону відповідальності. Наприклад, JsonAccountRepository відповідає виключно за читання та запис у файл, а AutomatedTellerMachine — за бізнес-логіку фінансових операцій.

* **Open/Closed Principle (OCP):** Система відкрита для розширення, але закрита для змін. Завдяки патерну Стратегія, ми можемо додавати нові способи видачі готівки (наприклад, "Видача в доларах"), просто створивши новий клас, не змінюючи ядро банкомата.

* **Dependency Inversion Principle (DIP):** Клас AutomatedTellerMachine залежить не від конкретного файлового сховища, а від абстракції IAccountRepository. Це дозволяє легко замінити JSON-файли на реальну SQL-базу даних у майбутньому.

* **DRY (Don't Repeat Yourself):** Уникнення дублювання коду. Замість того, щоб писати алгоритм розрахунку купюр двічі, ми винесли його у базовий абстрактний клас BaseDispenseStrategy, який наслідують інші стратегії.

* **KISS (Keep It Simple, Stupid):** Замість налаштування складної реляційної бази даних для локального симулятора, було обрано просте та ефективне зберігання даних у форматі JSON, що повністю задовольняє вимоги проєкту.

# Design Patterns

У проєкті імплементовано 3 поведінкові патерни проєктування:

* **[Observer (Спостерігач)](/Register/Core/AutomatedTellerMachine.cs)**

Для чого: Щоб відділити бізнес-логіку від візуального інтерфейсу Windows Forms.

Реалізація: Ядро генерує події за допомогою делегатів (наприклад, OnWithdrawResult, OnBalanceRequested). Клас форми підписується на ці події та оновлює UI (виводить MessageBox або змінює Label) лише тоді, коли ядро повідомляє про результат.

* **[Strategy (Стратегія)](/Register/Core/DispenseStrategies.cs)**

Для чого: Для динамічної зміни алгоритму видачі готівки залежно від вибору користувача на формі (галочка "Видати дрібними").

Реалізація: Створено інтерфейс IDispenseStrategy. Метод WithdrawFunds приймає цей інтерфейс як параметр і викликає розрахунок без прив'язки до конкретного алгоритму.

* **[State (Стан)](/Register/Core/AtmStates.cs)** 

Для чого: Для позбавлення від складних конструкцій if/else при перевірці статусу банкомата та картки (чи заблокована вона, чи введено пароль).

Реалізація: Створено інтерфейс IAtmState та класи IdleState (очікування), AuthenticatedState (авторизовано) та BlockedState (заблоковано). Банкомат делегує обробку дій поточному стану.

# Refactoring Techniques
У процесі написання та вдосконалення коду були використані такі техніки рефакторингу:

* **Extract Method** (Відокремлення методу): Логіка відображення історії транзакцій у ListBox була винесена в окремий метод LoadTransactionHistory(), що дозволило викликати його повторно як при вході в систему, так і після кожної нової транзакції.

* **Extract Interface** (Виділення інтерфейсу): Створення IAccountRepository та IDispenseStrategy з існуючих класів для зменшення зв'язності (coupling) системи.

* **Replace Conditional with** Polymorphism (Заміна умовного оператора поліморфізмом): Рефакторинг логіки перевірки блокування картки. Замість перевірки if (account.IsBlocked) перед кожною операцією, ми запровадили патерн State, де BlockedState автоматично відхиляє всі дії.

* **Replace Magic Number with Symbolic Constant** (Заміна магічного числа символічною константою): Максимальна кількість спроб введення PIN-коду була винесена в константу private const int MAX_ATTEMPTS = 3; у класі AutomatedTellerMachine, щоб зробити код читабельним та легким для налаштування.

* **Encapsulate Field** (Інкапсуляція поля): Усі моделі даних (Account, TransactionDetails) використовують властивості (get; set;) замість відкритих публічних полів, що захищає дані від некоректної модифікації ззовні.
